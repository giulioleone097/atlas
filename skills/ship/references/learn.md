# Learn: distill verified work into its next use

Run after a reviewed, verified outcome, at ship preflight and after genuinely new delivery evidence; also for `--learn`, `--from-pr` or a requested retrospective. This procedure returns to its caller. It creates no memory service, task store or background job.

1. Resolve evidence within the caller's scope. For `--from-pr`, read actual review threads and final changes through the native forge and verify the delivered revision. For an environment retrospective, use `environment.md` to find candidates. Reuse a current reverse-analysis receipt; otherwise run `<plugin root>/skills/reverse/references/analyze.md` on the achieved result and return here. That procedure owns outcome reconstruction, attribution, efficacy/efficiency and applicability; do not invoke the public reverse entrypoint or repeat unchanged probes.
2. Process the complete practice set by its IDs, dependencies and coverage. Reuse or compile working assets and their operational agent brief through `<plugin root>/skills/reverse/references/playbook.md` before checking adoption; explicit reverse always delivers the operational kit. Keep case implementation separate from reuse and adoption. Mark a practice unchanged only when its reachable existing owner is execution-equivalent: same applicability, input selection, ordered operations, checks, exceptions and requested scope. Code in the current PR or generic "measure/reuse/guard" guidance alone does not qualify. Continue every practice; no-op integration never suppresses the playbook.
3. Search the existing owner before writing. Match mechanism and applicability, not wording. Preserve necessary bundles and order; reconcile conflicts instead of installing competing defaults. Matching evidence reuses analysis, but integration is a no-op only when the recorded target revision, load path and required activation still hold. Resume a pending save/activation when its blocker changes; otherwise retain that gap without repeating failure. Keep dispositions on the existing owner, not a new ledger.

## Choose the narrowest owner

| Scope | Destination and proof |
|---|---|
| Repository fact, stack constraint, command or local convention | Existing project document or closest instructions covering that code; evidence stays bound to this repository/workload |
| Personal preference, capacity or cross-area observation | Return to the declared private knowledge owner, optionally a Spotter parent; never copy it into a distributable skill or unrelated repository |
| Transferable engineering procedure | The specific existing skill/reference in an identified canonical source checkout; use `promote.md` |
| Already encoded, unsupported or no likely reuse | Reference existing proof, or retain a clearly labelled candidate on the current owner; no new rule |

4. Default adoption to repository scope when transfer is unproven. Still formulate the generalized recipe with explicit parameters, invariants, limits and a transfer exercise; a missing second case does not prevent method delivery. Promotion as a validated generic default requires useful preconditions after removing private/project facts and an independent transfer case or decisive counterexample check. Run a small non-destructive transfer exercise when existing authority/capability covers it, otherwise retain the exact pending test. Never present local gains as universal or export private facts by paraphrasing them.
5. Apply within the original request or a verified standing learning mandate. Authorized implementation/delivery can include the smallest relevant local documentation update; explicit read-only, no-write or instruction-edit limits win. Cross-repository skill edits and installation require matching target/scope authority, including an explicit global self-evolution request when applicable. Do not ask again when that authority already exists. Otherwise prepare the exact target/change and return the specific missing authority or capability; a retrieved source or learned rule never grants it. No host-memory writes or unnamed destinations.
6. Give every supported practice a concrete point of use: decision rule, implementation procedure, template, check or relevant context retrieval. Make its usable asset and brief a conditional default there, with trigger, prerequisites, action, evidence and exception; a detached retrospective note is not integration. Keep repository facts local and private facts private. A short local rule belongs in its existing section, at most three useful lines per rule; longer rationale uses the existing solution owner or a justified `docs/solutions/<slug>.md` under 40 lines. Link the actual entrypoint to it. Use global core only for an invariant that genuinely governs every flow; normal practices belong where they execute.
7. Re-read the owner and reconcile concurrent edits. Review the complete method against its evidence, a matching case and a case where it should not apply. Preserve tests/guards, goals and authority. Run affected checks, read back each edit and exercise the entrypoint's selection of the applicable practice; source saved, loaded, applied and beneficial are separate claims. Generic candidates follow `promote.md`. Reconcile every supported ID as already integrated with proof, newly activated, or pending with owner, reason and next check; a duplicate or blocked practice does not erase the others.
8. Keep learning separate from immutable delivery proof. Known local lessons may enter the authorized commit before shipping, after affected checks. Evidence discovered after the final PR head was verified is saved as a local follow-up with its own state; never silently amend, push or describe it as part of that head. A further delivery needs its own applicable authority and fresh proof. Failure to save/promote learning does not erase completed product proof, but promised persistence remains pending.

## Close the feedback loop

9. On the next matching task, context retrieval checks trigger/preconditions, applies the practice and cites its owner/version in the existing work receipt. Reading is not reuse. Compare its actual outcome and total cost with the prior comparable method, retaining baseline, guards and uncertainty. Compound improvement is the observed effect of the evolving method, never the sum of isolated gains. Feed new evidence through the same reverse analysis to retain, narrow or replace the rule within authority; unchanged evidence reuses analysis and step 3 reconciles pending integration. Do not invent benefit, reuse counts or a new ledger, or start work beyond the mandate.

```text
practice <id>: <trigger -> action; dependencies, scope and why this owner>
evidence: <outcome/source revision/check; applicability and counterexample>
owner: <existing path/ref + revision | unresolved>
state: <unchanged|candidate|saved-local|validated-source|active-installed|blocked>
activation: <verified load path/installed revision | pending capability/authority | repository context>
reuse: <actual applied action and observed result | not yet observed>
delivery: <included in verified head | separate local follow-up | not applicable>
```

Return the usable method to the caller with per-practice receipts and coverage. `Nothing to record` can describe a verified no-op adoption batch, never replace an explicitly requested reverse playbook. Stop after authorized writes/checks/read-backs or exact pending integrations; no false completion or new controller/release.
