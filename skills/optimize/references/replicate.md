# Replicate a performance method

Use for an evidenced latency, payload, eager-dependency or graph-computation bottleneck. This is a construction guide for conditional candidates, not a guarantee that a technique wins. `metrics.md` owns measurement/acceptance; `worktrees.md` owns isolation, budgets and checkpoints.

## Fill the case parameters

Bind `control revision`, `candidate revision`, `workload/fixture`, `authorization/query scope`, `trigger`, `usable-ready predicate`, `cold/warm/return mode`, `transport/cache conditions`, `outcome metric`, `guards`, `measurement budget` and `equivalence check`. Choose readiness from a real permitted user interaction, not disappearance of a spinner. Choose cache keys from every dimension affecting data visibility/result. Keep original case constants out of the new recipe.

## Execution sequence

1. Retrieve applicable project reuse kits first; use their working assets through the supplied entrypoints, adapting specified seams and checking target contracts. Generic recipes below fill actual gaps, not replace available implementations. Build control and candidate separately with equivalent dependencies/configuration; record artifact hashes. Separate representative user journeys, empty states and scale-only fixtures. Keep fixtures and guards fixed.
2. Capture a diagnostic timeline: triggering action -> request start/end -> transfer/parse/compile -> computation/render -> usable interaction. Profiling locates the bottleneck; its overhead is not an acceptance measurement.
3. Choose only recipes below supported by that evidence. Reserve one candidate with a causal prediction, owned paths, expected artifact and falsifying observation; preserve the inherited allowance.
4. Validate behavior before timing: authorization/scope, values/order, selection, errors/retry, cancellation and real readiness. For writes include duplicate/conflicting requests, caller isolation and durability where the contract requires them.
5. Measure control/candidate serially in alternating or randomized order under the same serving protocol, compression and workload. Record raw samples, failures, paired deltas, spread and request/payload counts. Do not run builds, competing benchmarks or intrusive profiling alongside acceptance runs. `metrics.md` chooses sample counts and noise handling; small samples do not establish production-tail percentiles.
6. Reject broken guards, incomparable workloads and gains inside uncertainty. Retain useful failed attempts and their cause. Checkpoint accepted candidates; remeasure combinations against their actual parent rather than summing standalone gains.
7. Exercise a different matching input and a nonmatching one. Record conditional adoption at the real workflow owner, remaining gaps and next reuse observation; transport, fixture, cache or source changes reopen affected proof.

## Choose a recipe from the observed constraint

**R1 — A read begins only after a likely user intent.** Inputs: read-only operation, bounded intent signal, scope key and freshness/invalidation contract. Start the read on a meaningful hover/focus/touch intent, share one in-flight result by that key, and have the final consumer join or take the valid result. Fall back normally after absence/failure/staleness. Prove one physical read, identical data and isolation across scope changes; measure intent lead time separately. Reject speculative fan-out that delays foreground work.

**R2 — The first required read waits for application-bundle parsing.** Inputs: safe bootstrap point, already valid identity/permissions, route-derived resource and handoff key. Start only the eligible read before heavy code loads; make the initialized service consume it once, checking key/freshness and using its normal path otherwise. Verify network start precedes parsing and there is no duplicate or cross-user reuse. If identity or authorization is not ready, this recipe is inapplicable.

**R3 — Heavy modules remain in the eager dependency graph.** Inputs: production import graph/metafile, startup roots and actual open triggers. Trace static reachability to expensive code, split broad re-exports into cohesive entrypoints, redirect lightweight consumers and defer the real route/modal boundary. Extract small helpers that accidentally re-import the heavy component. Build, prove the heavy module left the static closure, and exercise every deferred opening/error path. Do not defer a component whose trigger/lifetime is unknown.

**R4 — Graph/list work repeats scans or traversals.** Inputs: ordering/duplicate/reference semantics, graph shape and repeated lookups. Index once per computation, memoize repeatable sub-results, maintain adjacency in place and stop reachability searches once answered. Distinguish the active recursion path from global visited state when detecting cycles. Check cycles, shared descendants and first/duplicate behavior; compare scaling on controlled sizes and separately measure representative user inputs. A scale win need not improve today's small cases.

**R5 — Navigation destroys still-valid data ownership.** Inputs: containing-page lifetime, query/auth key, freshness and write invalidators. Move the feed/resource owner above recreated child views, reuse it only inside that lifetime/scope, preserve view/query state, revalidate as required and refresh after successful mutations. Release on owner exit or scope change. Verify returns avoid duplicate reads and that permissions, query changes, transient errors and retry remain correct. Do not turn a page cache into unbounded global state.

**R6 — The next view can prepare without competing with the current one.** Inputs: actual foreground readiness, allowed next views and resource allowance. Wait for foreground content, then prepare eligible data/modules sequentially or within a measured bound; explicit user intent remains responsive. Recheck eligibility and cancel obsolete work. Hold the foreground response during validation: no background primary read may overtake it. Report placeholder visibility separately from real content; compare first switch, return and cold entry separately.

**R7 — Discovery downloads a full catalog to preserve selection.** Inputs: paging/search/facet contract, stable selected IDs and authorization scope. Separate selected identity/state from discovery pages, hydrate missing selected records, and return bounded pages plus full-scope facets. Share one owner between preview and modal, add bounded lookahead and reject obsolete responses. Verify deselection, global search, scroll, authorization and save readiness against the original behavior; visible card counts alone are insufficient. Choose page/lookahead sizes from the new viewport and budget, not old constants.

**R8 — A required write waits on unrelated queued work.** Inputs: transaction/caller context, response contract, idempotency scope and required side-effect durability. Separate the required commit from ancillary scheduling; preserve caller authorization and cancellation semantics. If allowed, commit in the request and bound ancillary scheduling by the actual contract. Coalesce identical in-flight work; use durable receipts when retries must survive contexts/processes, and reject conflicting payloads. Test dependency outage, occupied workers, duplicates and crash/retry boundaries. A timeout or in-memory map is not durable delivery; preserve required orchestration/outbox guarantees and compatibility until rollout proof exists.

**R9 — Backend work exceeds the authorized requested result.** Inputs: exact scope/query predicate, output/order contract and consistency boundary. Push precise filters down, remove unused includes/projections, hydrate only referenced records and reuse already-read facts to prove work empty. Preserve global authorization and selection semantics; use the needed snapshot boundary for multi-query consistency. Compare payload or explicit semantic equivalence and SQL/request counts, then time it. Reject split-query or query-merging changes that alter ordering/representative identity, multiply round trips, fail translation or merely trade bytes for latency.

Return the selected recipe, filled parameters, ordered patch plan, checks, measured/rejected result and adoption owner to the caller. A new performance case still needs its own evidence; no recipe grants publication, deployment or data-write authority.
