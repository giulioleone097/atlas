# Native goals and continuation

Use when binding, inspecting or changing native continuation, not as setup for every edit. For multi-stage work, inspect an available current-goal reader once and reuse its matching owner; load this contract when continuation is selected or state requires action. The issue owns acceptance and delivery; the plan/handoff links its native references. No second goal store, backlog, scheduler or public skill.

## Discover and bind

1. Inspect the current session's actual tools, native command dispatcher and supplied host state. Resolve goal read/create/replace/finish, session continuation, schedule create/read/update/cancel and their scope separately. A product name, installed binary, documented feature or another session's tool is not callable capability. Report a needed missing operation, not a blanket unsupported host.
2. Read the active native goal when possible. Match its condition, session/project and owner issue to this request. Reuse the enclosing goal; a child skill or worker never replaces or completes it. An unrelated goal stays untouched: do independent authorized work without attaching it, and request a decision only if a native mutation is necessary. Unknown goal state is not absence; do not create over it.
3. If no goal exists, create one when the user explicitly requests a goal or continued execution until a stated condition and the live host permits it. Wording such as "keep working until the checks pass" selects this route without requiring a slash command or a second confirmation. An ordinary implementation, outcome card, request to change these plugin instructions, brainstorming or schedule alone does not authorize creation. Bind one observable end state, proof, scope, permitted delivery and supplied limits; never invent token/time budgets. Without native activation, continue authorized work and report only the real capability gap.
4. Dispatch the supported native operation and read back the condition and session identity before reporting it active. Never use private IPC, provider state files, a custom MCP goal mutator, queued self-prompts or a shell loop. Printing `/goal ...` is not dispatch. If a native setter starts execution itself, that native run is the owner: observe/resume it rather than launching the workload a second time. If a command is user-invocable only, provide that command with `activation: not performed` and continue independent work. Do not launch a second CLI session to impersonate the current goal; a separate run requires the user's request and its own verified identity.

## Host routes

Codex's live schema and Claude documentation were checked on 2026-09-18; other hosts remain discovery hints. Current tools and permissions decide each operation. Goal means continuous work toward acceptance; loop means a requested time/event trigger. Neither expands authority or replaces the other.

| Host | Goal and continuation | Requested timing/event work |
|---|---|---|
| Codex | `get_goal` reads/reuses the owner; `create_goal` binds an explicit goal/continuous-until request. Current `update_goal` statuses are `complete`, `blocked`, and `paused` only at the user's explicit request. It is not a rename, resume or budget setter. | Codex desktop `automation_update`: thread heartbeat by default; standalone cron only for a requested standalone run. Inspect/update existing jobs through native controls; no shell scheduler. |
| Claude Code | Native `/goal` reads; `/goal <condition>` sets/replaces; `/goal clear` clears. Replacing/clearing needs matching authority. The host evaluates completion from surfaced evidence. | Native `/loop` or `CronCreate`, `CronList`, `CronDelete` per available schema. Session cron, durable tasks and cloud routines are different capabilities; inspect actual lifetime and timezone. |
| Cursor | Native `/goal` and built-in `/loop` where exposed. Do not assume Claude's read/clear semantics. | Native `/automate` or Automations controls for Cloud Agent schedules/events. A local agent or CLI does not inherit cloud capabilities automatically. |
| Antigravity | Native `/goal <condition>` where exposed; inspect its actual status/stop surface. | Native `/schedule` for one-time/recurring tasks where exposed; inspect timezone, lifetime and cancellation rather than writing sidecar processes. |
| Devin | Reuse the current native session/task and its actual continuation/status tools; no assumed `/goal` or Codex mutation API. | Native Scheduled Sessions where exposed; web support does not imply Devin CLI can create or inspect schedules. |
| ChatGPT Work / other hosts | Use only capabilities exposed in that session. An Atlas workflow MCP or uploaded skill does not supply Codex goals. | Use an available native scheduling surface, otherwise return a prepared instruction and name the missing activation capability. |

## Execute, resume and finish

At entry/resume, reuse the caller's bound mandate and feasible actions; only a direct, unbound entry reads `references/agency.md`. This lifecycle supplies only supported native continuation; the build controller owns action selection and adaptation even without a native goal.

5. Let the bound native goal drive continued turns; Atlas supplies the scope/build/review/authorized ship sequence. Before another slice, reconcile tracked owners and plan projections through `references/tickets.md`, reread relevant native state, reuse current proof and choose only ready work inside the agreed scope. Never re-enter setup, republish issues, repeat completed work or clear a goal to force a new turn.
6. Keep one execution owner per outcome. A goal and an observation-only monitor can coexist; a recurring callback must not execute the same issue while its native owner is active. Reuse the actual session/job reference. If ownership cannot be established, keep the callback read-only and report the gap rather than claiming an atomic lock. Do not add a competing Stop hook or poll loop.
7. On interruption, approval wait or capability failure, save the exact next action and confirmed native session/goal/job references on the existing issue/plan/handoff. Record the observation as dated, never authoritative persisted host state. On host switch, reread the issue, artifacts and the new host's actual goal; an old id or transferred Markdown does not transfer a live loop. Pending questions follow `<plugin root>/skills/scope/references/asking.md` and remain pending.
8. At the outer boundary verify the entire goal, including requested delivery and durable optimization checkpoints, before completion. A child, passed test or opened PR proves only its slice. Codex completion uses `update_goal` then `get_goal` only when achieved; blocked uses the live tool's repeated-blocker rule (currently three consecutive goal turns), never low budget or a stage return. On an explicit pause, use the advertised pause operation, report its returned status and stop goal work; never pause autonomously or invent a resume API. Where the host evaluates completion, surface exact proof and read its verdict. Stop/cancel only owned requested triggers; stopping a loop is not success.

## Requested loops and schedules

9. Prefer the host's native goal for an explicit continuous-until mandate, and native `/loop`/cron or Codex automation for a requested recurring/later/event check. Ask only for missing consequential timing/scope; reuse timezone, active window, notification preference and authority. A progress plan is not activation, and installation/ordinary work creates no trigger. Read existing jobs first and update/reuse a match; without discovery, preserve the gap instead of duplicating it. Session loops and durable schedules have different lifetime: inspect the live host, never promise survival across restart from a transferred reference.
10. Put a bounded callback in the native job: owner issue/plan, repository, intended skill, acceptance, original authority, execution owner, and when to stop. On wakeup, resolve current native ownership and reread artifacts before acting. Explicit scheduled reports produce the requested brief; additional monitors stay quiet on unchanged/non-actionable state. An unattended missing decision is saved for the user, not a question panel or implied approval. If no new evidence or changed approach can advance the work, preserve the blocker and let the host's supported wait/blocked lifecycle handle it; never spin on the same failure.
11. Verify mutation results and an independent native read/list when supported, including id, destination, prompt/scope, cadence/timezone and enabled state. An acknowledged creation with no independent read-back is `native result only`, not verified. Read back an ambiguous prior attempt before retrying. On completion or cancellation, stop only the finite job owned by this request when its terms require it; retain an ongoing user-requested cadence. Unavailable native activation leaves an honest on-demand workflow, never a background claim.

Report only relevant lifecycle facts alongside the caller's result: `native: <host/session> — <reused|created|completed|paused|waiting|unsupported|not requested>; evidence: <native read-back|native result only|unavailable>; trigger: <id/state|none>; next: <action|complete>`. A schedule setup request returns after this report; do not start its workload immediately unless requested.
