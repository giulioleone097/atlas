# Distill the directive; expand on demand

The deliverable is a small set of operating rules that compresses a proven method into a reusable instruction. Deep analysis supports a terse answer; response length is not analysis depth.

1. Start from the practices actually supported by analyze.md. Separate the engineering techniques from how they were discovered/verified. Group mechanisms that share one established concept; keep independent useful practices. Remove chronology, case identifiers, metrics and procedural narration from the directive.
2. Write one terse line of precise method names or short operating rules, separated by semicolons. Essential qualifiers stay attached to the method; steps, explanations and rejected labels remain in the human drilldown. If the final line retells the implementation, compress it again into concepts. Style example only: `KISS; DRY; SOLID; Hexagonal/Clean Architecture; Te2eD reale.` Its terms are not mandatory content. No fixed word quota, opaque invented acronyms or unsupported boilerplate.
3. A named principle carries its actual operational meaning. KISS, DRY, SOLID, Clean or Hexagonal Architecture belong only when requested or supported, never as an automatic slogan. Respect user-defined terms: Te2eD means development driven by real E2E tests; attribute it to a case only when the evidence shows those tests drove development, not merely a final test pass.
4. Keep the source-bound meaning behind each clause: practice ID, mechanism, applicability, dependencies, failure/exclusion condition and existing implementation/check where available. Preserve IDs across analysis, directive and adoption. A concise phrase must not hide a decisive authorization, identity, consistency or uncertainty condition; keep that qualifier in the directive when omission would change the action.
5. Test the compression: on a different matching input, can a competent agent select the known approach without reconstructing the original investigation? Can it recognize the meaningful exclusion? If ambiguity remains, refine the term or add the smallest qualifier/reference. New target requirements, including implied compatibility needs, still need evidence; original-case parameters are not the full target contract. Do not equate this usability check with demonstrated target benefit.
6. Separate presentation layers: concise, navigable drilldown helps the human understand and verify; the final agent layer is an isolated minimal directive. Always produce that final distillation, even after --drilldown or --kit. Keep evidence, adoption notes and supporting references before it; retain only decisive conditions inside it. A minimal-only request receives the directive alone. No mandatory file, pack, status table or tutorial is needed. Read-only still receives the directive without writes.
7. --drilldown or an explicit equivalent request expands only the useful causal/evidence branches and limitations, with native graph rendering where supported. --kit or an explicit request for code/assets expands the actual reusable implementations, exact source/revision, dependencies, USE/ADAPT/KEEP/VERIFY and focused integration checks. Existing working code is the starting point; redesign needs a concrete mismatch or a demonstrated better equivalent. An asset inventory alone is not the default directive.
8. Learning stores/updates the distilled rule at its authorized point of use and links its existing support. Private code/facts remain private. Verify execution-equivalent adoption separately from case implementation, documented knowledge and actual reuse. An unchanged adoption receipt never suppresses the useful directive; a compact response never implies an unperformed installation or universal gain.

Stop when the directive preserves the supported method and decisive limits, any requested expansion is delivered, and authorized persistence has a truthful state. "Fifteen words with substantial meaning" is a density goal, not permission to drop necessary meaning or a fixed output limit.
