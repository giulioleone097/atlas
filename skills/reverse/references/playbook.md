# Recover transferable causal principles

Reverse extracts why the successful method worked and turns that causal logic into reusable decision rules. Technique names, implementation summaries and generic slogans do not complete the distillation.

1. Use analyze.md's supported outcomes, mechanisms, alternatives and practice IDs. For each material strategy trace **constraint -> chosen intervention -> mechanism -> observed effect -> preserved invariant**. Distinguish measured contribution from inference and joint effects; retain unsuccessful alternatives that reveal the boundary.
2. Recursively abstract the resolved causal graph, not just the first technical layer: ask what makes each candidate principle work, which deeper relation its conditions express, and whether shared relations unify strategies without losing independent effects. Reuse resolved nodes; stop when further abstraction adds no actionable transfer or would exceed the evidence. Climb from means to principle: remove domain objects and technology names, then state the causal relationship that remains useful elsewhere. For example, repeated requests plus retained valid state can support avoiding repeated work and reusing still-valid results; “use caching” names only the software means. Do not infer an entire design philosophy from a matching word or retrofit a requested label without supporting practice.
3. Express each distinct principle as an actionable decision rule with the condition or limit that makes it sound. Interpret “use always” as a standing criterion for choosing actions, not an unconditional instruction to repeat a particular intervention. Anticipation, automation and reuse still depend on relevance, contention, validity and constraints. Separate established evidence, a transferable inference and an unvalidated universal claim.
4. Before accepting **each** principle, run the transfer gate: restate its rule using domain-neutral actors/resources/constraints/outcomes; apply that same rule to a concrete non-software situation; identify a counterexample and narrow its condition. Another screen, library, service or software system is not this cross-domain check. If the rule still requires the original technical objects to prescribe the action, recurse into the underlying relationship again or classify it as domain-specific rather than a transferable principle. Check information cost, deadlines and reversibility: uncertainty does not automatically prohibit every decision unless a hard guard requires it. A worked analogy is a transfer hypothesis, never a measured new success. Revise failed principles inside this workflow before output/adoption, without requiring the user to rewrite them.
5. Keep the support traceable: principle -> original practice IDs -> source/evidence -> actual implementation or check. Preserve independent strategies and meaningful bundles without multiplying synonyms. Familiar principles qualify only when the analysis shows how they affected this result; avoid a stock list of KISS/DRY/SOLID. Attribute Te2eD only when real E2E tests demonstrably drove development, not merely verified it afterward.
6. Present a concise human drilldown that explains those causal choices, limits and transfer checks, then finish with a self-contained set of transferable operating principles for the next agent. Keep original technical objects in the evidence/examples, not in the final rule when they restrict it to software. Use as many short rules as the distinct mechanisms require; never force one sentence or fifteen words. Compress repetition and implementation detail, not the causal logic or applicability needed to act. A keyword line can be an index, never the sole deliverable when it loses that meaning.
7. --drilldown expands the relevant evidence/graph; --kit opens actual assets with source/revision, dependencies and USE/ADAPT/KEEP/VERIFY. Both still end in the transferable principles. A minimal-only request receives the compact rules without the human explanation, preserving decisive conditions. No mandatory files or package: reuse the existing evidence owner.
8. Learning stores the principle at its authorized point of use with linked support and appropriate scope. Keep private facts/code private. Case implementation, documented principle, validated transfer, reachable adoption and actual reuse remain separate claims; broader validation governs promotion, not whether a conditional principle can be delivered. Missing persistence never becomes a false integration claim.

Stop when the operating principles explain the supported strategies, survive a stated cross-domain challenge at the claimed level, retain decisive limits and have truthful adoption status. Brevity is successful only while that transferable value remains.
